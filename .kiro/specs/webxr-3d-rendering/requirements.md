# 需求文档 — WebXR 3D 房间渲染

## 简介

WebHarness.Chat 目前只有 2D 网页视图：聊天记录在 `static/index.html` 里渲染为垂直滚动列表，富文本（Markdown、图片、语音、```chart / ```mermaid / ```svg / ```a2ui 代码块）由 DOM 渲染管线呈现。本规格新增「3D 渲染端」：同一份聊天记录，在 3D 场景中以空间化方式呈现（消息面板悬浮、数据图原生 3D 化、成员以 3D 形象站立、语音以空间音频播放），支持桌面 3D 预览与 WebXR 沉浸式（VR 头显）两种进入方式。

**核心不变量（延续既有架构决策，见 docs/generative-ui.md）**：聊天记录只存「数据（dataModel / chart JSON / 图片与语音等原始资源）+ 形式与意图（组件树 / 图类型）」；样式归渲染端。因此 3D 渲染端是**又一个渲染端**——除个别基础项外，服务器与聊天记录格式不需要为 3D 做改动。

### 术语

- **渲染端**：消费同一份聊天记录的视图实现。2D 网页是现有渲染端；本规格新增 3D 渲染端。
- **面板（Panel）**：3D 场景中承载一条消息渲染结果的平面/弧面，内容以纹理贴图呈现。
- **面板模式**：把消息在 2D 管线里已经渲染好的 DOM 栅格化成纹理贴到面板——所有内容类型的通用兜底。
- **原生 3D 模式**：不经过 DOM，直接用消息里的**数据**（chart JSON、a2ui 组件树、图片资源）重建 3D 图形——数据与渲染分离的直接收益。
- **桌面 3D 预览**：不用头显，在普通浏览器里以轨道/行走视角查看 3D 场景。
- **沉浸式（immersive-vr）**：通过 WebXR Device API 在 VR 头显中进入场景。
- **形象（model3d）**：用户账号已有的 3D 形象字段（GLB/GLTF 文件 ≤20MB 或外链 URL，含 ARKit 52 表情 / Unity Humanoid 骨骼两个能力标志）。

## 需求 1：3D 入口与模式选择

**用户故事**：作为人类用户，我要在聊天页一键进入当前房间的 3D 视图，随时退回 2D，两种视图看到的是同一间房、同一份记录。

### 验收标准

1. 聊天顶栏 SHALL 新增「3D」入口按钮；点击后加载 3D 渲染端（首次按需加载模块，不拖慢 2D 首屏）。
2. WHEN 浏览器支持 WebXR 沉浸式（`navigator.xr.isSessionSupported('immersive-vr')` 为真）THEN 入口 SHALL 同时提供「沉浸式」进入方式；不支持时只提供桌面 3D 预览，不报错。
3. 3D 视图 SHALL 常驻「返回 2D」操作；返回后 2D 视图状态（房间、滚动位置、未读）不丢失。
4. 3D 渲染端 SHALL 复用 2D 端既有的房间消息获取/增量轮询逻辑（同一 token、同一 API），不新建第二套会话。
5. 2D 模式 SHALL 保持现状且为默认模式；3D 属于可选视图，任何 3D 故障 SHALL NOT 影响正常聊天。

## 需求 2：聊天记录的空间化呈现（面板模式）

**用户故事**：作为人类用户，我要在 3D 房间里像站在一块环幕前一样阅读聊天记录，所有 2D 里已有的富文本（Markdown、表格、图片、语音、图表）都能原样看到。

### 验收标准

1. 3D 场景 SHALL 将房间消息渲染为一圈弧形/环形消息墙：最新消息靠近用户正面，按时间顺序排列，旧消息沿弧线向两侧延伸。
2. WHEN 消息数量超出可视弧长 THEN SHALL 支持阅读导航（拖拽旋转 / 键盘平移 / 头显传送或手柄拨动），并 SHALL 支持跟随最新（停在最新消息处，新消息到达时面板滑入）。
3. 面板内容 SHALL 采用面板模式：复用 2D 管线对同一条消息生成的 DOM，栅格化为纹理贴到面板。因此 Markdown、```mermaid、```svg、```chart、```a2ui、图片、语音、引用、灰色私聊样式在 3D 中 SHALL 与 2D 外观一致（仅承载形式不同）。
4. WHEN 一条消息被撤回、更新（流式追加）或用户无权查看（服务端抹空）THEN 3D 面板 SHALL 与 2D 行为一致地更新/消失，无第二套内容逻辑。
5. 面板 SHALL 显示发送者头像 + 用户名 + 时间（与 2D 气泡头部一致）；私聊面板 SHALL 保留灰色样式标识。
6. 文字纹理 SHALL 保证中文清晰可读（栅格化分辨率随面板大小自适应；中文字号过小时允许用户走近查看）。
7. WHEN 消息墙沿时间方向排到更早、仍有未加载的历史 THEN 3D 端 SHALL 支持向前分页加载（经服务器新增的只读 `beforeId` 参数一次性回填，2D 行为不变）。

## 需求 3：结构化数据的原生 3D 渲染（数据驱动模式）

**用户故事**：作为人类用户，我希望 Agent 发的数据图在 3D 里不只是"一张贴图"，而是立起来、可走近观察的 3D 图形——这才体现把数据与渲染分离的价值。

### 验收标准

1. WHEN 消息含 ```chart 且 type=bar/line THEN 3D 渲染端 SHALL 以真实 3D 几何体（柱体/折线）渲染同一份 JSON 数据，含标题、数值标签与图例；数据与 2D 饼/柱/折线一致。
2. WHEN ```chart type=pie THEN 3D SHALL 渲染为 3D 饼/环（挤出扇形）；点击或指向某扇区 SHALL 显示该扇区名称与数值。
3. WHEN 消息含 ```a2ui THEN 3D 渲染端 SHALL 优先以原生 3D 小部件渲染目录 v1 组件：MetricCard（悬浮指标）、Progress（3D 进度条）、Callout（浮标提示）、Timeline（空间时间线）、Row/Column/Card（空间布局组）、Text（3D 文本）；Table、Divider 与未知组件 SHALL 回退面板模式；PieChart/BarChart/LineChart SHALL 走需求 3.1/3.2 的原生图表。
4. WHEN a2ui 组件含 dataModel 数据绑定（JSON Pointer）THEN 原生 3D 小部件 SHALL 同样解析绑定取值，与 2D 语义一致。
5. 目录约定不变：3D 渲染端按 catalogId 严格解析，未知组件渲染占位（`[a2ui: 类型名]` 的 3D 版本），绝不因新组件崩溃。
6. 图片消息 SHALL 以带边框的纹理平面挂在消息位上；指向/走近可放大查看。
7. ```mermaid 与任意 ```svg SHALL 以面板模式承载（示意图不做 3D 重建，避免语义失真）。

## 需求 4：成员 3D 形象（GLB / GLTF / VRM）

**用户故事**：作为人类用户，我要在 3D 房间里看到其他在线成员的 3D 形象站在房间中（这用上账号早已预留的 model3d 字段），没挂形象的人显示缺省化身。

### 验收标准

1. WHEN 在线成员设置了 model3d（文件或外链）THEN 3D 场景 SHALL 加载并放置其形象；未设置的 SHALL 显示稳定的缺省化身（由用户名生成的颜色体 + 名牌，与 2D 缺省头像同一配色逻辑）。
2. VRM 文件 SHALL 被接受并加载：服务器上传校验本就按 glTF 魔数判断（VRM 即带 VRM 扩展的 GLB），`_validate_model3d_bytes` 与 20MB 限制不变；3D 端按文件内容识别 VRM 扩展并用 VRM 加载器处理。
3. WHEN 模型勾选「支持 Apple ARKit 52 表情」THEN 3D 渲染端 SHALL 支持 52 个 ARKit blendshape 的驱动接口（说话口型、预设表情可映射到 VRM 表情或直接驱动 morph target）。
4. WHEN 模型勾选「支持 Unity Humanoid 全身骨骼」THEN 3D 渲染端 SHALL 支持人形骨骼动画驱动（VRM 动画 / glTF 动画剪辑播放，如挥手、待机）。
5. 形象加载失败（外链失效、文件损坏、格式不支持）SHALL 静默回退缺省化身，不影响场景其余部分。
6. 形象 SHALL 有名字牌（用户名 + 在线状态）；房主 SHALL 有可辨识标识。
7. MVP 阶段成员形象为静态站位（按用户名稳定散列排位，避免每次进房站位乱跳）；实时位姿同步不在本规格范围（见设计文档「暂缓项」）。

## 需求 5：语音消息的空间呈现

**用户故事**：作为人类用户，我希望语音消息在 3D 里像"从发送者方向传来"，同时保留文字转写可读。

### 验收标准

1. WHEN 一条语音消息进入 3D 场景 THEN SHALL 渲染语音面板（转写文字 + 播放/时长，与 2D 一致），播放 SHALL 使用空间音频：声源位于发送者形象/消息位，随用户视角产生方位感与距离衰减。
2. WHEN 成员无 ARKit/Humanoid 标志或形象加载失败 THEN 口型不做要求；语音只做空间播放。
3. 语音消息的私聊规则、30 秒撤回规则 SHALL 与 2D 一致（服务端已保证，3D 端不得绕过）。

## 需求 6：交互与可读性

**用户故事**：作为人类用户，我在 3D 里的操作要少而直觉：转着看、走近看、跟着最新消息走。

### 验收标准

1. 桌面 3D 预览 SHALL 支持鼠标拖拽旋转、滚轮缩放、键盘/按钮移动；沉浸式 SHALL 支持手柄指向传送或推杆平移（不支持手柄时允许头朝向走动或原地环视）。
2. 所有面板/图表 SHALL 保证在用户正常视距下字号不小于可读阈值；提供「聚焦模式」（对准一条消息放大到舒适阅读）。
3. 3D 中 SHALL 提供发送消息的最小入口（文本发送即可；输入复杂富文本引导回 2D 输入框）。语音/私聊等复杂操作 3D 端 MVP 不要求。
4. 界面文案 SHALL 支持现有 zh/en 双语（复用 2D 的 i18n 键，新增键同结构补齐）。

## 需求 7：性能与稳定

**用户故事**：作为人类用户，3D 模式不能把浏览器/头显拖垮，退出后资源要还干净。

### 验收标准

1. 面板纹理 SHALL 按需生成并缓存；同一条消息的纹理 SHALL NOT 在每帧重绘。消息更新时对应纹理失效重建。
2. 场景中同时驻留的面板/形象数量 SHALL 有上限（超出的旧消息降级为不可见或低分辨率，靠近时再加载）；纹理内存峰值 SHALL 在移动端浏览器可承受范围。
3. 渲染循环 SHALL 在页面不可见（2D/3D 切走、标签页后台）时暂停。
4. WHEN 返回 2D 或切换房间 THEN 3D 场景 SHALL 释放纹理、几何体与加载器资源（dispose），长会话内存 SHALL NOT 持续增长。
5. 低端设备（不支持 WebGL2 / XR 会话失败）SHALL 回退 2D 并提示，不出现黑屏死页面。

## 需求 8：不变量与服务器边界

**用户故事**：作为维护者，我要确保 3D 是纯渲染端增量，聊天记录与 Agent 生态不被 3D 改动绑架。

### 验收标准

1. 聊天记录内容格式 SHALL NOT 因 3D 改变：仍只存数据 + 形式/意图（Markdown、chart JSON、a2ui 消息、附件），不存任何 3D 专属样式（颜色、坐标、材质）。
2. Agent API 与 skill.md 语义 SHALL NOT 改变：Agent 发消息时不需要知道人类用 2D 还是 3D 阅读。
3. 服务器改动 SHALL 限于两处：`GET /api/rooms/{room_name}/messages` 增加只读可选 `beforeId` 翻页参数（不传即旧行为，消息格式与 Agent API 语义零变，供 3D 端向前回填历史）；必要时细化 `_validate_model3d_bytes` 对 VRM 的识别提示（VRM 现状已可上传）。实时位姿同步等新端点明确列入暂缓项，不在本规格。
4. 3D 渲染端代码 SHALL 独立成文件（不继续膨胀 index.html 单文件），2D 渲染管线对 3D 只暴露「消息 → DOM」与必要的状态接口。
5. 版本号 SHALL 按惯例递增（仓库当前 2.9.3 → 3D 首版 2.10.0），发布沿用现有 tar.gz + install.sh 流程，发布前先做生产备份。
